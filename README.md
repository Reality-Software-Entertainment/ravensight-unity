# Ravensight for Unity

Official Unity SDK for [Ravensight](https://ravensight.io) player analytics.

Sessions, batched events, an offline queue, rate limit handling, a saved player
opt-out and the server side kill switch, in one MonoBehaviour and no third party
dependencies.

* API base: `https://api.ravensight.io` (`/api/v1` is appended)
* Docs: https://ravensight.io/docs/
* Privacy: a random per-install device id, no advertising identifier, a saved
  player opt-out (`Ravensight.SetTrackingEnabled(false)`) and a reset
  (`Ravensight.ResetDeviceId()`), no tracking permission prompt needed. What
  your store label can say: https://ravensight.io/docs/#privacy-label
* Unity 2021.3 or newer declared; verified on Unity 6000.6.5f1 only
* Public builds (demos, jam entries, open source games): no key means no
  analytics, an opt-in consent mode and a distribution label. See
  [Public builds](#public-builds).

## Install

Unity Package Manager, add by git URL:

```
https://github.com/Reality-Software-Entertainment/ravensight-unity.git
```

Window > Package Manager > `+` > Add package from git URL, paste the line above.

Or add it to `Packages/manifest.json` yourself:

```json
{
  "dependencies": {
    "com.realityse.ravensight": "https://github.com/Reality-Software-Entertainment/ravensight-unity.git"
  }
}
```

To pin a version, append a release tag such as `#v0.5.0` to the URL once that
tag exists.

**Upgrading from a copied 0.2.0.** If you followed the 0.2.0 workaround and
copied this repository into `Packages/` (or `Runtime/` into `Assets/`), Unity
gave those files random local GUIDs. The `.meta` files shipped from 0.2.1 use
different ones, so after you switch to the git URL, or copy 0.2.1 over the
old files, every scene or prefab holding the Ravensight component shows
"Missing (Mono Script)" and the SDK no longer starts, with no error from the
SDK itself. Do one of these:

* Keep your GUID. If you stay on a copy, overwrite only the `.cs` files and
  keep your own `.meta` files. If you move to the git URL, note the `guid:` in
  your old `Runtime/Ravensight.cs.meta` first, then replace it with the
  package's (`6ccf49fe13fb64dd283edfe488f55079`) in each scene and prefab
  that uses the component (text search, with Asset Serialization set to Force
  Text).
* Or re-add the component. After switching, add **Ravensight Analytics** to its
  GameObject again and fill in its Inspector fields (the ingest key and any
  setting you changed).

When moving to the git URL, delete the old copy so the package is not
imported twice.

## Quickstart

1. Create an empty GameObject in your first scene, name it `Ravensight`.
2. Add the **Ravensight Analytics** component to it.
3. Paste your publishable ingest key (`gt_live_...`) into the Ingest Key field.
   For a game whose source or builds anyone can download, leave it empty
   and inject it at build time instead (see [Public builds](#public-builds)).

That is the whole setup. The component survives scene loads, queues
`game_started`, reads the server kill switch, opens a session and starts
flushing on a timer. In the Editor it sends nothing unless you turn on
**Send From Editor** (see [Editor play mode](#editor-play-mode)).

Then track from anywhere:

```csharp
using System.Collections.Generic;
using RealitySE;

public class LevelController : MonoBehaviour
{
    private void OnLevelCleared(int level, int deaths, float seconds)
    {
        Ravensight.Track("level_completed", new Dictionary<string, object>
        {
            { "level", level },
            { "deaths", deaths },
            { "seconds", seconds },
        });
    }
}
```

`Track` calls made before the component wakes (from another script's `Awake`,
say) are held, up to 500, and queued when it wakes, after the player's saved
choice has been read.

Prefer to configure it in code instead of the Inspector? Call this once, before
your first event:

```csharp
Ravensight.Initialize("gt_live_your_key");
// or start it switched off, and turn it on later with SetEnabled(true):
Ravensight.Initialize("gt_live_your_key", false);
```

## API

Everything game code needs is static on `Ravensight`:

| Call | What it does |
| --- | --- |
| `Ravensight.Track(name, data)` | Queues an event. `data` is optional. Returns false when tracking is off. Never sends by itself, except that a full batch of 50 starts a flush. |
| `Ravensight.Flush()` | Sends queued events now. Returns a `Task<RavensightFlushResult>`. After the key was refused it still makes one attempt. |
| `Ravensight.SubmitFeedback(message, category, rating)` | Posts player feedback. Throws `RavensightException` on failure. |
| `Ravensight.FetchSuggestions()` | EXPERIMENTAL. AI generated design suggestions for your game. An empty list, with no request, while tracking is off. |
| `Ravensight.SetTrackingEnabled(bool)` | The player's choice. Saved in `PlayerPrefs` at once and read on every launch. Callable before the component exists. |
| `Ravensight.IsTrackingEnabled` | The player's saved choice, for the initial state of your toggle. |
| `Ravensight.ResetDeviceId()` | Forgets this install's identity: a new random id, the queue cleared, the session dropped. Returns the new id. |
| `Ravensight.SetEnabled(bool)` | The developer's runtime switch, not saved. For debug or server builds, not for a player toggle. |
| `Ravensight.IsEnabled` | True only while the SDK is collecting. False when inert (no key), switched off, opted out or not yet opted in, switched off by the server, or after a refused key. |
| `Ravensight.DeviceId` | This install's random id. Null while inert, and with Consent set to Opt In before the first yes. |
| `Ravensight.Initialize(key, options)` | Creates the component from code with a `RavensightOptions`: `ApiUrl`, `GameVersion`, `Enabled`, `Consent`, `Distribution`, `Optional`. |
| `Ravensight.StatusReason` | Why events are not being sent, or null when ready. See [Startup outcome](#startup-outcome). |
| `Ravensight.StatusChanged` | `event Action<string>`, raised with the new reason when it changes. |
| `Ravensight.LastInitResult` | What the startup check found, or null until it has finished. |
| `Ravensight.SessionToken` | The open session's token, null until one opens. See [Game servers](#game-servers-and-the-session-token). |
| `Ravensight.IsPlaytest` | True when a Ravensight Playtest run launched this build. |
| `Ravensight.SetPlaytestContext(token, runId)` | For builds that cannot read environment variables, such as mobile. Call before the component wakes. |
| `Ravensight.IsReady` | True once a session exists. |
| `Ravensight.TrackPurchase(amount, currency, itemType, itemId, ...)` | A purchase. See [Typed events](#typed-events). |
| `Ravensight.TrackResource(flow, resource, amount, ...)` | A resource gained (`source`) or spent (`sink`). |
| `Ravensight.TrackProgression(status, p1, p2, p3, score, ...)` | A progression step: `start`, `complete` or `fail`. |
| `Ravensight.TrackError(severity, message, stack, ...)` | An error, with a severity from `debug` to `critical`. |
| `Ravensight.SetErrorCapture(bool)` | The game's runtime switch for automatic error capture, not saved. |
| `Ravensight.IsErrorCaptureActive` | True while automatic error capture runs. |
| `Ravensight.Client` | The underlying `RavensightClient` for anything else. |

Event values can be strings, numbers, bools, nulls, nested dictionaries or
lists. They are serialized by the SDK's own JSON writer, because Unity's
`JsonUtility` cannot round trip a dictionary.

### Feedback

The category is one of `RavensightClient.FeedbackCategories`: `bug`,
`suggestion`, `complaint`, `praise`, `playtest`, `other`, or null for none. The
rating is 0 for none, or 1 to 5. Anything else fails locally, with no request,
as `invalid_category` or `invalid_rating`. While tracking is off it fails
locally as `disabled`.

```csharp
try
{
    await Ravensight.SubmitFeedback("The boss fight drags", "suggestion", 3);
}
catch (RavensightException e)
{
    Debug.LogWarning("feedback rejected: " + e.Code);
}
```

## Inspector settings

| Field | Default | Meaning |
| --- | --- | --- |
| Api Url | `https://api.ravensight.io` | Only change this if you self host. Whitespace, trailing slashes and a trailing `/api/v1` are stripped, then `/api/v1` is appended. Empty means the default. |
| Ingest Key | none | Your publishable `gt_live_...` or `gt_pub_...` key. Empty makes the SDK inert for the run. |
| Optional | off | Silences the one warning an inert start (no key) logs. |
| Game Version | empty | Empty uses `Application.version`. |
| Auto Flush Seconds | `15` | Seconds between timer flushes. `0` flushes only on demand, on a full batch, on background and on quit. |
| Max Queue Size | `500` | Offline queue cap. Oldest events are dropped first. |
| Request Timeout Seconds | `15` | Per request timeout. |
| Enabled On Start | on | The developer's start switch, not saved. Off means no request of any kind until `SetEnabled(true)`. |
| Consent | Opt Out | Opt Out: on until the player opts out. Opt In: nothing is sent and no device id is made until `SetTrackingEnabled(true)`. |
| Distribution | empty | A short label sent on the session, such as `native-release`. At most 40 characters, no control characters. Empty sends none. |
| Send From Editor | off | Send from play mode in the Unity Editor. |
| Track Lifecycle Events | on | Sends `game_started` and `game_exited`. |
| Track Pause Events | off | Also sends `game_paused` and `game_resumed`. |
| Session Timeout Seconds | `1800` | iOS and Android: time in the background after which returning starts a new session. |
| Performance | off | Opt in to per session frame rate sampling and one `health` event. See [Typed events](#typed-events). |
| Error Capture | on | Automatic error capture. Untick to opt the game out. See [Automatic error capture](#automatic-error-capture). |
| Verbose Logging | off | Logs SDK activity to the console. Warnings you need to act on are always logged. |

## Automatic events

With Track Lifecycle Events on, the SDK sends exactly two events of its own:

* **`game_started`**, queued in `Awake` with the real start time, first in the
  queue. The server kill switch is read before it is sent. Never queued while
  the client is disabled or the player has opted out; if tracking is turned on
  later in the run, it is queued then, once.
* **`game_exited`**, queued once on the quit path. On desktop players the quit
  is held for at most 1.5 seconds while the last batch is sent. Delivery is best
  effort: a process that ends first can lose it. Desktop focus loss is not an
  exit; it flushes and sends no event.

`game_paused` and `game_resumed` are only sent when Track Pause Events is on.

**iOS and Android.** Going to the background sends no event. The SDK records
the time, flushes, and saves a small marker (`ravensight_bg` in `PlayerPrefs`).
On iOS that flush runs without a background task, so the system may suspend
the app before it finishes; anything unsent stays queued for the next flush.
On returning:

* after less than Session Timeout Seconds (30 minutes by default), nothing is
  queued and the session carries on;
* after 30 minutes or more, `game_exited` is sent under the old session with the
  time the app left, the session ends, and `game_started` opens a new one.

If the app was killed in the background (swiped away), the next launch finds
the marker and, unless the player has opted out or the session has expired,
sends that `game_exited` once before anything else. One attempt, then the
marker is deleted whatever the answer.

## Startup outcome

`Ravensight.StatusReason` is null when the SDK is ready, otherwise one of these
values. `Ravensight.StatusChanged` tells you when it changes.

| Reason | Meaning |
| --- | --- |
| `no_key` | Started with no ingest key. Inert for the run: nothing is stored or sent. Logged once unless Optional is on. |
| `disabled` | Switched off with Enabled On Start, `SetEnabled(false)` or Send From Editor, or the player opted out (or, with Consent set to Opt In, has not said yes yet). |
| `invalid_key` | The ingest key was refused. On the startup settings check or on opening a session (`401`, or a `403` other than the ones below), the run ends: the queue is cleared and nothing more is sent until the next launch. On a later batch `403` automatic sending stops, events stay queued and `Flush()` makes one more attempt. Logged once as a warning. |
| `tracking_disabled` | Tracking is switched off for this game on the server. The queue is cleared and nothing more is sent this run. Logged once. |
| `offline` | No connection, a timeout or a server error. Events are kept and retried. |
| `rate_limited` | The server asked the SDK to wait. Events are kept. |
| `session_failed` | A session could not be opened, or a playtest token was refused or came without a run id. |
| `playtest_job_closed` | The playtest job this run belongs to has finished. Sending stops for the run. |

```csharp
Ravensight.StatusChanged += reason =>
{
    if (reason == "invalid_key") Debug.LogError("Check the Ravensight ingest key.");
};
```

## About your ingest key

The `gt_live_...` key is publishable. It is safe to ship inside a build: it can
open sessions, read the tracking kill switch and read this game's design
suggestions. It cannot read analytics, read feedback or touch your account.
Rotate it from the dashboard at any time.

## Public builds

For a game anyone can download, fork or play: a demo, a game jam entry, an
open source project. A game that sets only its key behaves as on 0.2.1,
apart from the refused key and jitter changes listed in the CHANGELOG.

* **Use a public key, injected at build time.** Create a public `gt_pub_...`
  key for the game in the dashboard and never commit it. Leave the Ingest
  Key field empty in the scene, and pass the key from a file your build
  script writes and your `.gitignore` lists, for example:

  ```csharp
  // Assets/Scripts/Generated/BuildSecrets.cs, written by the build script, gitignored
  internal static class BuildSecrets { public const string RavensightKey = "gt_pub_..."; }

  // in your first scene
  Ravensight.Initialize(BuildSecrets.RavensightKey, new RavensightOptions
  {
      Consent = RavensightConsent.OptIn,
      Distribution = "native-release",
  });
  ```

  Ship a placeholder `BuildSecrets.cs` with an empty key in the repository
  so a clone still compiles.
* **No key, no analytics.** With an empty key the SDK is inert: it reads and
  writes nothing in `PlayerPrefs`, builds no network transport, makes no
  request and runs no flush timer, and every call is a quiet no-op.
  `Ravensight.StatusReason` and `LastInitResult` say `no_key`. It logs one
  warning; tick **Optional** (or `RavensightOptions.Optional`) to silence it.
  So a clone or a development build sends nothing.
* **`Ravensight.IsEnabled`** is true only while the SDK is collecting. Use it
  to skip work that only feeds analytics.
* **Consent: Opt In** sends nothing until the player says yes. No device id is
  made and not even the settings check is sent before
  `Ravensight.SetTrackingEnabled(true)`. Events tracked before the yes are
  dropped, not held for later; events tracked right after it are queued while
  the settings check runs. The yes is saved in `PlayerPrefs` as
  `ravensight_optin`, beside the existing `ravensight_tracking_enabled`, and
  `SetTrackingEnabled(false)` removes it. Saying no again stops everything but
  keeps the device id; `ResetDeviceId()` forgets it. `SetTrackingEnabled` and
  `IsTrackingEnabled` save and report the choice even while inert, so the
  settings toggle always shows the right state. The default, **Opt Out**,
  keeps the 0.2.1 behaviour.
* **Distribution** is a short label of your own, such as `native-release`,
  `web-demo` or `jam-build`, sent on the session as `distribution` so you can
  tell builds apart. At most 40 characters and no control characters; a label
  that breaks either rule is not sent and is logged once. Empty sends none.
* **`rs_event_id`** is added to every event's data: the first 16 characters
  of the device id, the start time in hex, an 8 hex character value made once
  per launch from the platform's secure random generator, and a counter. It
  always matches `^[A-Za-z0-9_-]{1,64}$`. A batch sent again after a failure
  carries the same ids, and the server drops a repeat. The queue lives in
  memory, so events still queued when the game exits are not sent on the next
  launch.
* **A refused key ends the run.** A `401` or `403` to the settings check or to
  opening a session (other than `tracking_disabled` and a refused playtest
  token) means the key was revoked, rotated or is wrong, and a retry cannot
  help. The SDK stops for the rest of the run: queue cleared, nothing more
  sent, one warning, status `invalid_key`. A later `SetTrackingEnabled(true)`
  saves the choice but restarts nothing; the next launch tries the key again.
  A `401` on a batch still means the session expired: a new one is opened
  first.
* **Jitter.** A failed request is retried after the backoff times a random
  factor between 0.5 and 1, never sooner than half a second and never later
  than 5 minutes. A server's `Retry-After` is obeyed exactly.
* **Events over 8,192 bytes** of data as the server measures it (JSON bytes,
  with a typed error's message and stack counted one byte a character; the
  name and timestamp are not counted) are dropped before they are queued,
  with one warning for the run. `Track` returns false for each.

What a request carries: the settings check sends only the `X-API-Key`
header; the session sends `deviceId`, `gameVersion`, `platform`, `sdk`,
`device` (see [Device id and privacy](#device-id-and-privacy)) and, when set,
`distribution` and `joinToken`; a batch sends `events`, each with `event`,
`data`, `timestamp` (unix milliseconds) and, for an event from an earlier
session, `origin`; feedback sends `message` and the optional `category` and
`rating`.

## How delivery works

* **Batching.** Up to 50 events per request, the server hard limit. `Track`
  only queues; a send happens on the timer, as soon as 50 are queued, on
  `Flush()`, on background and on quit. A flush keeps sending batches until the
  queue drains.
* **Persisted queue.** On by default (Persist Queue in the Inspector). The
  queue is kept in one file per ingest key,
  `Application.persistentDataPath/Ravensight/queue-<hash>.json`, written
  through a temporary file and an atomic replace, so a partial write never
  replaces a good one. It is written at most once a second while events
  arrive, at once after every delivered batch, on background and on quit,
  and read back at start. Events survive a crash,
  a kill or a lost network and go out on the next launch. At most 500 events
  are kept, oldest dropped first, and anything older than 89 days is dropped
  at start (`Stats.Expired`). Max Queue Size caps the queue in memory.
* **Original session, build and platform.** Each event remembers the session
  it was tracked under (the opaque `origin` the server returned). An event sent
  on a later launch carries it, so the server stores it under the run it
  happened in. A saved exit whose session has expired is queued under that
  origin too. The origin is kept only in the queue file and never logged.
* **Errors behind gameplay.** Automatically captured errors queue behind
  gameplay events, never inside a batch awaiting an answer, and a full queue
  evicts a capture before any gameplay event; an incoming capture with no
  capture to evict is dropped. The flag is kept in the queue file, so the
  rule holds after a restart, and a capture is written at once, without its
  `rs_trail`, which stays in memory only.
* **Removed only once delivered.** Events leave the queue, and the file, only
  after a `2xx`, or a `400` that names them by `index`.
* **Answers.** A `400` with `index` drops that event and resends the rest;
  `400 batch_too_large` halves the batch, and a single event still too large is
  dropped; any other `400` drops the request's events (each logged once). A
  `401` opens one new session and resends with the same ids; a second `401` in
  a row waits for the backoff. A `403` on a batch keeps the events and stops
  sending until the next launch. `413` splits; `415` resends once uncompressed.
* **Rate limits.** A `429` waits exactly `Retry-After` seconds, and so does a
  `503` that carries one. With no such header the SDK backs off exponentially
  from 10 seconds to a 5 minute ceiling, each wait times a random factor
  between 0.5 and 1 (never under half a second), so many players who lost the
  network together do not come back together. `Flush()`, a move to the
  background and quit cut a backoff short, never a `Retry-After`.
* **Compression.** A batch of 1,024 bytes or more is sent gzip compressed.
* **Signed requests.** When `POST /session` answers with `signing` (sessions
  opened with a public key), every batch carries `X-Ravensight-Timestamp` and
  `X-Ravensight-Signature: v1=<hex>`, an HMAC-SHA256 of
  `v1:<timestamp>:<body>` over the uncompressed body, with the device clock
  corrected by the server's time. The secret is kept in memory only.
* **Event ids.** Every event's data carries an `rs_event_id`, kept across
  resends and launches, so the server drops a resend whose first copy was
  stored as a duplicate (within its duplicate window, 24 hours by default).
* **Kill switch.** `GET /settings` is read at boot, before any batch is sent
  (the one exception is the saved exit of an app killed in the background,
  described above). A `403 tracking_disabled` from any request has the same
  effect.
* **Nothing while off.** While the client is disabled, the player has opted
  out, the server has switched tracking off or the run is stopped, the SDK makes
  no request of any kind.

## Ads and attribution

```csharp
// A paid impression in micros of the currency: 0.0015 USD is "1500".
Ravensight.TrackAdRevenue("admob", "rewarded", "level_end", "1500", "USD");

// AdMob's OnPaidEvent: AdValue.Value is already micros.
Ravensight.TrackAdMobPaidEvent(adValue.Value, adValue.CurrencyCode, "admob", "rewarded", "level_end");

// A mediation callback that reports a double in major units (MAX, LevelPlay):
Ravensight.TrackAdRevenueFromMediation(adInfo.NetworkName, adInfo.AdFormat, adInfo.Placement, adInfo.Revenue, "USD");

// Clicks, rewards and failures carry no revenue.
Ravensight.TrackAd("admob", "rewarded", "rewarded", "level_end");

// Where this install came from, once per device.
Ravensight.SetAttribution("store_referrer", network: "google", campaign: "spring");
```

`TrackAd(network, format, result, placement, revenueMicros, currency)` sends one
`rs_ad` event. Format is `banner`, `interstitial`, `rewarded`, `native`,
`app_open` or `other`; result is `shown`, `clicked`, `failed` or `rewarded`.
Revenue is a digit string of whole micros, sent only with `shown`, always with
a three letter currency, never converted. `RavensightDelivery.MicrosFromRevenue(0.0015)`
and `MicrosFromDecimalString("0.0015")` both give `"1500"`, rounding half up
past six decimals on the decimal digits, never by multiplying a float. The
helpers return false and send nothing for a value the server would flag, such
as revenue without a currency.

`SetAttribution(source, network, campaign, adset, creative, touchTimeMs)` sends
one `rs_attribution` event per device id: `ravensight_attribution_sent`, stored
beside the device id, makes later calls return false across restarts. Pass
`Ravensight.DeviceId` to an attribution partner as its customer user id before
the partner starts, so its install callback names this device.

## Levels and deaths

The dashboard's level funnel, per-level deaths and journeys read your event
names and the place fields `level`, `location` and `track`. To say exactly what
an event is, set `rs_kind` in its data to `level_start`, `level_complete`,
`death` or `none` (`none` opts an event out of the name match). Keys that start
with `rs_` are reserved for Ravensight.

```csharp
Ravensight.Track("checkpoint_reached", new Dictionary<string, object>
{
    { "level", "forest_2" },
    { "rs_kind", "level_complete" },
});
```

The full rules are at https://ravensight.io/docs/#detection-rules.

## Typed events

Four helpers send the reserved `rs_*` properties the dashboard reads for
revenue, economy, progression and errors. They are thin wrappers over `Track`,
so queueing, batching, retries and the player's opt out behave exactly as for
any event, and they return what `Track` returns. Every helper takes an
optional `extra` dictionary (the reserved keys win over it) and an optional
`eventName`. They never throw on bad input: a wrong value is sent and the
server flags it, which shows on the Implementation health card.

```csharp
// Money is whole minor units: 499 is 4.99. An integer or a digit string.
// The currency is upper-cased. Default event name: "purchase".
Ravensight.TrackPurchase(499, "usd", "gem_pack", "gems_100",
    cart: "cart_7", transactionId: "txn_123");

// flow is "source" or "sink". Default name: "resource_source" or "resource_sink".
Ravensight.TrackResource(RavensightTyped.Source, "gold", 250, itemType: "quest", itemId: "q7");

// status is "start", "complete" or "fail". Default name: "progression_<status>".
Ravensight.TrackProgression(RavensightTyped.Complete, "world1", "level2", score: 1500);

// severity is debug, info, warning, error or critical. The message is cut to
// 200 characters and the stack to 2000. Default name: "error".
Ravensight.TrackError(RavensightTyped.Error, ex.Message, ex.StackTrace);
```

## Automatic error capture

On by default (Unreleased). Errors in a live game become ordinary `error`
events, each one event on the usual meter, so you see them in the Errors view
without writing any code.

What is captured, through `Application.logMessageReceivedThreaded`:

| Unity log type | Becomes |
| --- | --- |
| `Exception` (an unhandled exception Unity logged, or `Debug.LogException`) | an event with `rs_source` `uncaught`, `rs_severity` `error`, `rs_error_type` from the exception line (`NullReferenceException`) and the stack Unity gives |
| `Error` and `Assert` (`Debug.LogError`, failed asserts) | an event with `rs_source` `log`, `rs_severity` `warning`, `rs_error_type` `Error` or `Assert` |
| `Warning` and `Log` | never an event; a trail line only, when the trail is on |

It also observes `AppDomain.CurrentDomain.UnhandledException` (`uncaught`)
and `TaskScheduler.UnobservedTaskException` (`unhandled_rejection`). It only
observes: other subscribers still run, the exception is never marked
observed, and nothing about how your game handles errors changes. One
exception that Unity both logs and raises is sent once.

When it runs: only with a key, after the player's consent (with Consent set
to Opt In, after `SetTrackingEnabled(true)`), while the SDK is enabled, while
the Error Capture field is ticked, and while the game's Errors switch on the
server is on. The switch arrives on the settings and session answers; when it
is absent capture is on. Errors raised during boot, before that answer, are
held in memory (at most 5) and sent once the answer says capture is on, or
discarded unsent if it says off. Opting out, `ResetDeviceId()` or
`SetEnabled(false)` stops capture at once and forgets anything held.

Bounded on the device, per session: at most 30 captures, 3 of the same error
(type, message with numbers and ids replaced, and first frame of your code),
and 6 a minute. Over a limit the error is dropped silently. Your gameplay
events always go ahead of captured errors in the queue, and when the queue is
full a captured error is dropped first. A `413` answer is handled like a
`400`: the batch is split and the one bad event dropped.

What is never sent: before queueing, the message and stack are scrubbed on
the device. Emails become `[email]`; bearer tokens, JWTs, `gt_` keys and runs
of 32 or more base64 or hex characters with a digit (other than a file path
made of ordinary words) become `[token]`; IPv4
and IPv6 addresses become `[ip]`; `/Users/<name>`, `/home/<name>`,
`C:\Users\<name>` and `C:\Documents and Settings\<name>` become `~`, the whole
name, spaces included; URLs lose any `user:password@`, their query and fragment. An IPv6 match
needs a digit, so `Face::Add` stays. Each field is cut to 4 times its limit
before scrubbing, then the message to 200 characters and the stack to 2,000. Lines the SDK itself logs,
and errors thrown from the SDK's own code, are never captured. Manual
`TrackError` calls are unchanged: they are never blocked by the switch, and
their text is sent as you wrote it and scrubbed by the server.

The trail (off unless the game's trail switch on the server is on): an
in-memory ring of the last 20 lines (log lines, warnings, earlier errors and
the names of events you tracked), each `+<ms since session start> <level>
<text>`, scrubbed and cut to 120 characters. It is sent only with a captured
error, at most 1,500 characters and on at most 10 errors a session, never on
its own and never written to disk.

To opt out, untick **Error Capture** on the component, or:

```csharp
Ravensight.Initialize(key, new RavensightOptions { ErrorCapture = false });
// or for part of a run
Ravensight.SetErrorCapture(false);
```

### Performance

Tick the Performance field in the Inspector (or set
`RavensightConfig.Performance` when you build the client yourself) to opt in.
The component then reads `Time.unscaledDeltaTime` once a second in `Update`,
keeps at most 600 samples, and sends exactly one `health` event per session
with the median and 10th percentile frames per second, memory in MB and boot
time in milliseconds. It is sent when the app goes to the background on iOS and
Android, and when it quits on desktop, never from `Update` itself. With no
sample taken, nothing is sent. It is off by default.

## Device id and privacy

The SDK generates a random device id on first run (`dev_` plus 32 hex
characters from the platform's secure random generator) and stores it in
`PlayerPrefs` under `ravensight_device_id`. No hardware identifier, advertising
id, IP based fingerprint or personal data is collected by the SDK itself.
Besides the events you send, the SDK sends:

* **Device fields**, once per session on `POST /session`: `model`
  (`SystemInfo.deviceModel`), `osVersion` (`SystemInfo.operatingSystem` with
  the OS name removed) and `gpu` (`SystemInfo.graphicsDeviceName`). Unity
  reports these without a permission prompt; none is a hardware identifier.
  Each is at most 128 printable characters. The server derives the country
  itself; the SDK never sends one.
* **Attribution**, once per install, only when the game calls `SetAttribution`.
* If you switch Performance on, one `health` event per session carries frame
  rate, memory and boot time.

The persisted queue file holds queued events and each session's opaque origin
stamp; never the session token or signing secret.

**Backups.** The queue file holds origin stamps and scrubbed error captures,
so it stays out of backups. On iOS the SDK marks it excluded from iCloud and
device backups (`NSURLIsExcludedFromBackupKey`, through the package's
`Plugins/iOS` file): the temporary file is marked before it replaces the
queue file, a failure is logged once (without a path) and retried on the
final file, and the folder and any older file are marked at start. A failed
write, and every delete, removes the temporary file too. On Android, Auto
Backup copies app files by default; add these rules to your backup rule files
(Unity writes `persistentDataPath` to the external files directory by default,
or the internal one with Write Permission set to Internal, so exclude both):

```xml
<!-- in your fullBackupContent file -->
<exclude domain="external" path="Ravensight/" />
<exclude domain="file" path="Ravensight/" />

<!-- in your dataExtractionRules file, inside both <cloud-backup> and <device-transfer> -->
<exclude domain="external" path="Ravensight/" />
<exclude domain="file" path="Ravensight/" />
```

Point the `<application>` element of your Android manifest at those files
with `android:fullBackupContent` and `android:dataExtractionRules`. Desktop
platforms have no app backup the SDK can opt out of.

The player's choice is stored by the SDK under `ravensight_tracking_enabled`.
`Ravensight.SetTrackingEnabled(false)` saves it at once, discards anything still
queued and stops all requests. It is read again on every launch, before
anything is sent, and it wins over Enabled On Start. You can call it before
the component exists.

```csharp
Ravensight.SetTrackingEnabled(false);        // the player opted out, remembered
string newId = Ravensight.ResetDeviceId();   // forget this install's identity
```

`ResetDeviceId` saves a new random id, clears the queue and drops the session,
so nothing links the old id to the new one.

A game that sends gameplay events and nothing else can declare Device ID and
Product Interaction as not linked to the player and not used for tracking,
and needs no tracking permission prompt. The row by row answers for the App
Store and Google Play forms are at https://ravensight.io/docs/#privacy-label.

## Telling players

You do not need a permission prompt, but saying what the game sends is good
manners. A paragraph your game can show, in a settings screen or on its
store page:

> This game sends anonymous gameplay events (what happens in the game, never
> who you are) to Ravensight so we can improve it. You can turn this off in
> Settings at any time.

And the toggle behind "turn this off":

```csharp
// an "Analytics" switch in your settings screen
public void SetAnalytics(bool on)
{
    Ravensight.SetTrackingEnabled(on);   // remembered across launches
}

// a "Forget me" button: a fresh random identity from now on
public void ForgetMe()
{
    Ravensight.ResetDeviceId();
}
```

Use `Ravensight.IsTrackingEnabled` for the switch's initial state.

## Editor play mode

Pressing Play in the Editor sends nothing by default, so your test sessions do
not show up as players. Turn on **Send From Editor** on the component to send
from play mode. While it is off, `SetEnabled(true)` does nothing in the Editor.
Player builds are not affected.

## Playtest

When a Ravensight Playtest run launches a desktop build, the SDK picks up the
run from the first of: `Ravensight.SetPlaytestContext(token, runId)`, the
environment variables `RAVENSIGHT_PLAYTEST_TOKEN` and
`RAVENSIGHT_PLAYTEST_RUN_ID`, or the command line arguments
`--ravensight-playtest-token=` and `--ravensight-playtest-run-id=`. During a run:

* the device id is `pt-<runId>`, kept in memory; the saved id is never read or
  written, and nothing else is written to `PlayerPrefs`;
* every request carries the `X-Ravensight-Playtest` header, and events are
  tagged as synthetic;
* the player's saved opt-out is ignored, and `SetTrackingEnabled` and
  `ResetDeviceId` do nothing but log one line;
* when the job closes (`403 playtest_job_closed`) or the token is refused,
  sending stops for the run.

A token without a run id never runs as a real player: the SDK stops with
`session_failed` and logs once.

## Game servers and the session token

`Ravensight.SessionToken` (the same value as `Ravensight.Client.SessionToken`)
is the open session's token, null until a session opens. Send it to your game
server, which can pass it on as `joinToken`. A headless server build that uses
this SDK creates its own client with the token as `JoinToken`; the first
session it opens sends it as `joinToken` alongside the device id. When the
token is valid, the server joins that player's session; otherwise the client
opens a plain session instead.

```csharp
var config = new RavensightConfig
{
    IngestKey = "gt_live_your_key",
    DeviceId = playerDeviceId,
    JoinToken = tokenFromThePlayer,
    Storage = new RavensightMemoryStorage(),
};
var client = new RavensightClient(config, new RavensightUnityTransport(this), null);
client.Begin();
await client.InitAsync();
```

The SDK never computes a session id on the client.

## WebGL

WebGL builds should work, with two caveats (not yet verified in a browser):

* `PlayerPrefs` is backed by IndexedDB and some browsers clear it aggressively,
  so returning players may look new.
* Quit is unreliable in a browser tab. Flush at points you control, such as the
  end of a level, rather than relying on quit. The same applies to the
  Performance `health` event, which is sent on quit and may never be sent in
  WebGL.

## Architecture

```
Runtime/
  Core/                           no UnityEngine dependency, enforced by asmdef
    RavensightClient.cs           sessions, batching, backoff, opt-out, lifecycle
    RavensightPlaytest.cs         where a playtest run's token and run id come from
    RavensightStorage.cs          IRavensightStorage plus an in memory version
    RavensightTransport.cs        IRavensightTransport plus request and response
    RavensightJson.cs             small JSON reader and writer
    RavensightErrors.cs           error capture rules: scrub, caps, trail, thread-safe inbox
  Ravensight.cs                   MonoBehaviour singleton, timers, app lifecycle
  RavensightErrorHooks.cs         the log and exception hooks, drained on the main thread
  RavensightPlayerPrefsStorage.cs IRavensightStorage over PlayerPrefs
  RavensightUnityTransport.cs     IRavensightTransport over UnityWebRequest
Tests/Editor/                     the Core suite in the Unity Test Runner (EditMode)
Tests/Runtime/                    the component booted in Play Mode
Tests~/Core/                      the .NET project for the same Core suite
```

`Runtime/Core` is its own assembly with `noEngineReferences` set, so a stray
`using UnityEngine` in the protocol layer is a compile error rather than a
surprise. That is what makes the logic testable without the Editor.

## Remote config and experiments

Version 0.3.1 fetches public configuration when a session opens. Use defaults
immediately and subscribe before initialization to refresh your game UI:

```csharp
Ravensight.ConfigReady += () => {
    double speed = Ravensight.GetConfigNumber("speed", 1.0);
    bool enabled = Ravensight.GetConfigBool("tutorial", true);
    string title = Ravensight.GetConfigString("title", "Welcome");
};
// Optional manual refresh; no polling is necessary.
await Ravensight.FetchConfig();
```

`GetConfigJson(key, fallback)` returns a defensive copy of object/array values.
Getters never coerce strings into booleans or numbers. Keep secrets out of config;
these values are public game settings. A fresh fetch costs one event; unchanged
responses send the exact cached ETag and return a free 304. Offline failures keep
validated cache scoped to API host, ingest key, device, platform and game version.
Opt-out clears this cache, and reset or late responses cannot restore the old
identity's values. Inactive clients return your defaults and send no requests.

A fetch alone is not an exposure. The first typed read (`GetConfigString`,
`GetConfigBool`, `GetConfigNumber`, `GetConfigJson`) in a session exposes the
player to every experiment the config lists: the SDK sends one `rs_exposure`
event, and every event queued after it in that session carries
`rs_exp_<key>: <variant>`. Events queued before the read stay untagged, a new
session (after the background timeout) starts untagged until its own first
read, and an experiment missing from a later fetch is no longer tagged.
Queued events keep the tags they were queued with, across launches. A well
formed `rs_exp_<key>` of your own is left alone; a malformed one is replaced. Config-ready fires after a completed refresh,
including offline fallback. Inspect the returned boolean to distinguish a
successful fresh/304 response from offline fallback. Responses are bounded to
50 keys, 8 KB per value, 20 nested levels and 10 experiments.


## Screenshot Player Reports

```csharp
// Redact first. EncodeToPNG() is a Unity Texture2D method; capture is application-owned.
var report = new RealitySE.RavensightReport("The door is stuck", texture.EncodeToPNG());
var receipt = await RealitySE.Ravensight.SubmitReport(report);
if (!receipt.Complete) {
    // Pending/processing is not success. Retain report and retry it later.
    receipt = await RealitySE.Ravensight.SubmitReport(report);
}
```

The helper accepts PNG only, at most 1,000,000 bytes and 4 million pixels. It
copies bytes, generates the client ID and capture time once, and uses the active
SDK session. Presigned HTTPS multipart uploads carry no SDK key or session token
and do not follow redirects. The server validates/sanitizes the image. A returned
`pending` or `processing` receipt needs another explicit attempt with the same
report object; exceptions are surfaced with no automatic text fallback. Do not
construct a replacement object to retry an uncertain request. Session/device or
endpoint changes and consent revocation stop retries instead of rebinding them.
Retry state is memory-only. Screenshot reports reserve 20,001 weighted events;
text-only reports use 1. Unfinished reservations expire server-side. No screenshot
is captured automatically and no image-analysis claim is implied.
